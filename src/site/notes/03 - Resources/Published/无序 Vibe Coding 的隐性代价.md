## 你的团队快了 3 倍，然后呢？

你的工程团队引入了 AI 编码工具。PR 数量翻倍，feature 交付周期缩短，开发者说体验很好。季度汇报上，这是一个漂亮的故事。

六个月后，你可能面对的是另一个故事：一个没人能维护的代码库，一份越来越高的 AI API 账单，以及一群困惑的工程师 — 他们不理解为什么工具明明在变强，交付却在变慢。

这不是每个团队的必然结局，而是我认为值得提前防范的风险：没有质量约束的产出加速，可能把今天省下来的时间变成明天的维护债。

## 两种 AI 编码，本质不同

2025 年初，Andrej Karpathy 创造了 "vibe coding" 这个词：你给 AI 一个 prompt，接受它生成的所有代码，不看 diff，跑起来就行，报错了就把错误信息贴回去再试。人是 prompt DJ，不是工程师。

一年后，Karpathy 自己提出了 "agentic engineering" 来描述另一种工作方式：AI agent 做实现，人做架构师和 reviewer，每个 diff 都经过审查，测试覆盖是前提而非可选项。

这两种方式的区别不在于是否使用了 AI，而在于是否把理解、验证和交付责任留在工程流程里。一个很直接的检查问题是：**你是否在 review 代码？** 但有 review 还不够，测试、架构约束和部署门禁同样属于这个区别。

Vibe coding 有它合理的使用场景 — 周末 hackathon、低风险个人脚本、快速验证一个想法。在这些场景下，可以主动接受更低的可维护性来换速度；涉及凭据、真实数据或不可逆操作时，安全底线仍不能省。问题是，把同样的低约束方式带进长期维护的生产系统，管理层看到的可能是"产出速度提升了"，看不到的是质量正在以隐蔽的方式下降。

## 退化可能形成正反馈，不只是一笔静态债务

这是本文最重要的论点，值得慢慢说。

AI agent 生成的代码中，可能夹带一些不符合预期的东西。注意，这里不只说 bug — 测试和运行时检查也不一定能捕获所有 bug。更隐蔽的是那些"不致命但不对"的东西：冗余的抽象层、违反项目架构约定的实现、因为 context 不足而选择的次优方案、不符合团队实践却被 AI 延续的 anti-pattern。

有效的 review 和自动化约束能拦截其中一部分。如果缺少这些检查，问题就更容易留在代码库里；有人签过 review，也不等于问题已被全部发现。

然后事情开始加速。

现代 AI 编码工具通常会把代码库中的相关文件加载到上下文中作为参考。当那些"不致命但不对"的代码累积起来，又被检索或直接读到时，agent 可能把它们当作项目惯例，生成更多风格相似的代码。后续任务继续引用这些实现，就可能延续错误。这取决于上下文选择、规则约束和验证机制，不是代码一变多就必然发生。

**我担心的是一个正反馈退化循环：低质量代码累积 → 被纳入 context → agent 以此为范本 → 生成更多低质量代码 → 后续继续引用。** 这是可检验的机制假说，不是本文已经测出的增长定律。

一笔静态技术债只影响当前代码；反馈循环还可能影响未来的生成方向。这个区别足以让管理层重视，但不能据此断言退化必然指数增长。本文没有能确定增长曲线的数据。

如果你的团队在用并行 agent 工作流 — 多个 agent 同时处理不同任务 — 同一份低质量参考可能被同时复制到多个分支，放大修正和集成的负担。但 agent 数量不能直接换算成退化倍数；任务隔离、合并门禁和共享上下文的方式都会改变结果。

用工厂来类比：这就像质检环节被取消后，生产线上的次品被当作原材料送回了生产线。

## 退化的第二重代价：Token 成本的恶性循环

代码质量退化的代价不只是"代码变难维护"。它还有一个管理层更容易感知的后果：AI 的使用成本在上升，而产出在下降。

当架构持续退化、代码库变得混乱，agent 推进相关任务可能变得更艰难。它可能反复尝试不同的实现方案，重构和重写之前的代码，查询更多相关文件来理解系统状态。这些额外尝试和查询会消耗 token，但并非每种任务都会受到同样影响。

更糟糕的是，当上下文被大量低质量代码和重试过程占满，关键约束可能更难被检索和利用。如果工具的上下文管理没有纠正这一点，产出质量可能进一步降低，又需要更多轮重试。

这可能形成第二重恶性循环：**架构退化 → agent 推进困难 → 重试和上下文负担上升 → 产出质量下降 → 架构进一步退化。** Token 上升是这个假说的一个可观测信号，不是单独证明机制成立的证据。

最讽刺的结局是：引入 AI 编码工具的初衷是降本增效，而无序使用的结果是增本降效。管理层会看到 AI API 账单逐月攀升，但很可能把原因归结为"用量增长"，而不是"效率下降"。

## 为什么管理层特别容易踩这个坑

因为短期指标全是正面的。

PR 数量上升了。Feature 交付周期缩短了。开发者满意度调查显示大家很喜欢新工具。在季度回顾中，这些数字讲述的是一个成功故事。

退化的信号是滞后的。代码库的腐烂不会在写代码的时候暴露，它会在改需求的时候暴露、在系统扩展的时候暴露、在排查线上事故的时候暴露。而这些时刻可能在六个月甚至一年之后才到来。

Token 成本的上升趋势同样容易被误读。当团队规模不变但 AI 账单持续增长时，直觉反应是"我们在更多地使用 AI，这是好事"。很少有人会去追问：每个 feature 的 token 成本是在上升还是下降？如果是上升，为什么？

等到问题暴露时，重写的成本可能已经超过了之前省下的所有时间。

## 该怎么做

这不是一篇反 AI 的文章。AI 编码工具是真正的生产力杠杆，前提是用对。以下是管理层应该推动的几件事：

**Review 不是可选项。** 对长期维护的生产系统，架构决策、模块边界、接口设计必须有人把关，不需要每一行都人工审查。Review 不是唯一闸门，更不是万能保证：类型检查、架构规则、隔离验证、属性测试、保留测试集和部署门禁要共同阻断风险。把 AI 生成的代码当作一个能力很强但不了解你项目历史的新人写的 PR — 你不会不 review 就合并一个新人的 PR。

**Spec 先行。** 在让 agent 动手之前，先把需求写清楚。模糊的 spec 在单 agent 环境下容易带来返工；在并行 agent 环境下可能带来多个方向各异的实现，合并时才发现互相矛盾。Spec 是重要约束，但清晰需求也不自动保证实现正确。

**测试先行（Red/Green TDD）。** 如果测试是在实现之后写的，agent 可能写出"验证实现恰好做了什么"的测试，而不是"验证实现应该做什么"的测试。先从需求写测试、确认失败、再实现，是一条有价值的防线；但同一个 agent 也可能在测试和实现里重复误解，或只满足已知用例。关键验收条件要有独立核对，结合人工审查、隐藏用例或独立生成的验证，不把先写测试等同于证据独立。

**投资架构。** 好的架构约束了 agent 的解空间，让正确的做法成为最简单的做法。清晰的模块边界、明确的接口契约、一致的代码风格 — 这些在传统开发中是"最佳实践"，在 agent 时代是"基础设施"。它们有望减少试错和查询负担，但是否降低 token 与总成本，应在具体项目里测量。

**监控 token 效率，而非 token 总量。** 每个已验收 feature 的 token 消耗和费用趋势可以是代码库健康度的辅助信号，不是诊断结论。比较时尽量控制任务难度、模型与版本、计费、缓存、上下文策略和验收口径；同时看返工、缺陷逃逸、review 负担和交付周期。如果 token 与返工一起上升，再去检查架构和上下文。本文没有比较实验支持它比质量扫描更灵敏。

若系统还会提炼 memory、Skill 或默认规则，误判就可能从一次代码范本传播到未来行为。经验候选应保留来源、适用条件，经独立验证与版本化批准后才发布，并能撤回；这是另一条传播路径，不等于已经证明所有记忆系统都会退化。

**控制验证债务，不只盯已合并代码。** 未验收产出持续增加时，风险在合并前就已积压；一旦这些产出被当成下游事实，还会扩大未来核对范围。我建议按风险、等待时长和下游依赖观察积压，设置未验收在制品上限，必要时降并行、缩小切片。不能把“通宵生成了更多代码”当成“交付更多价值”。

**把复杂度当显式预算。** 除功能正确，还要说明新增抽象、状态、依赖、迁移和外部影响为什么必要。少写代码也可能把复杂度藏进黑盒或配置；目标不是最小行数，而是在质量与业务约束下限制长期负担。上述预算与上限是工程建议，效果要在具体项目中观察。

## 门槛没有降低，它升高了

每一次软件工程的抽象跃迁 — 从汇编到高级语言，从手写代码到框架，从单机到云 — 都让更多人能参与软件构建，同时让专业工程师的价值向更高层次迁移。AI 编码是这条弧线上的又一步。

机械性的编码工作正在被自动化。架构判断、质量判断、取舍判断正在成为更重要的价值中心。它们不是唯一重要的能力，领域知识、实现技能和协作仍不可少；但不能再把判断当作编码之外的附加项。

管理层的责任不是禁止 AI 工具 — 那是逆潮流而动。管理层的责任是确保团队在用 agentic engineering 而不是无约束的 vibe coding 来构建生产系统。把测试和自动化门禁一起算上，我仍然会追问这个管理问题：

**有人在 review 吗？**

如果答案是"没有"，又没有可靠的验证和质量责任人，你就在让未经检验的实现不断定义后续上下文。它不一定立刻腐烂，但这不是值得拿生产系统下注的工作方式。
