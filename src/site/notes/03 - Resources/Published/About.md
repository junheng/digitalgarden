## 关于本网站

Diomgis' Nexus 是一个关于 **Agentic Engineering** 的实践笔记。

这里不讨论"AI 会不会取代人类"这类话题。这里讨论的是更具体的问题：怎么设计一个能持续运转的 agent 系统？怎么在 agent 管线中分配人类和脚本的职责？怎么让 harness 的能力补偿随模型与任务变化而调整，同时保留必要的行动接口、治理与验收？

如果你在落地 agent 系统时遇到了类似的问题，这里的一些笔记可能对你有用。

## 作者的研究方向

作者的日常工作涵盖以下领域：

**Agent 系统设计与落地**。不满足于"用 agent 写代码"——关注的是 agent 系统的工程化：harness 架构、管线设计、多 agent 协作、评估体系。核心信念是 HIL（Human-in-the-Loop）：让系统在已授权范围内由 agent 自动驱动，人类在关键决策节点做判断，也补位 AI 尚不成熟的环节。能力补位可以在验证后减少，但授权、权限、隐私、审计、幂等与独立验收的责任，不会因为模型变强就自动退出。

**软件架构**。云端架构设计、领域驱动设计（DDD）、微服务治理。在 agent 时代，"好架构"的定义正在从"人容易理解"扩展为"agent 容易在其中工作"——好的架构让边界、目标和接口更清楚，尽量让正确的做法成为最简单的做法。文字约束仍可能被误解，关键权限和禁止动作需要由运行环境落实。

**技术管理**。20-40 人团队的管理经验。关注 agent 对团队结构、招聘标准、组织形态的深层影响。核心观点：agent 正在压缩只执行、不承担判断与验证的工作模式；团队仍需给成员同等上下文、训练和合理升级通道。

**当前探索**：agent 管线的形式化设计（script-as-pipeline-node）、meta-harness（让 AI 设计自己的 harness）、评估飞轮的工程实现。

## 技术理念

- **HIL 优先**：让 AI 在授权范围内尽量自动执行，人类在关键节点做判断；自动化不等于责任和批准边界消失
- **Build to Delete / Build to Last**：用于补偿当前模型能力缺口的安排，应有可测试的退出条件；行动接口和长期治理职责持续承重，实现则可以替换。同一组件可能同时承担这几类功能，不能整体按「模型变强了」一删了之
- **约束与指令配合**：明确不能做什么，也明确目标、成功标准和例外处理。约束在某些任务里比长篇操作指令更有效，但不是永远优越；权限与安全边界由宿主执行，不只靠文字要求
- **异步沟通优先**：更深的思考，更少的打断
