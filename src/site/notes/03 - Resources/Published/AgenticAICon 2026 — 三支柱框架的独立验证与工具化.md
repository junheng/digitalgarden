## 来自 AgenticAICon 2026 的文献对照与框架修正

在[上一篇分析](https://nexus.sigmoid.cc/Agentic%20Steering%20%E4%B8%89%E6%94%AF%E6%9F%B1/)中，我提出 Agentic Steering 的三支柱：目标设定、过程设计、评判反馈。木桶是我的诊断比喻，不是已证明的完备结构。

2026 年 7 月 2—3 日，我参加了杭州的 AgenticAICon 2026。本文以这次参会为线索，比较相关论文和公开项目，看它们实际解决什么，也看它们迫使我的框架修正什么。参会经历不替代证据：下面把论文事实、项目说明和我的解释分开。

**2026-10-14 的修订使用了当时已公开的论文版本，包括会后更新。** 它不是对大会发言的逐字复现。文件名中的“独立验证”保留以维持已有链接，但正文不再把这些研究当成三支柱框架的确认实验。

## 目标支柱：自进化可能带来风险，但不是一种已证实的统一机制

### Misevolution 实际研究了什么

Shuai Shao、任启涵等人的 *Your Agent May Misevolve: Emergent Risks in Self-evolving LLM Agents*（arXiv 2509.26354），研究模型、记忆、工具与工作流四种进化路径的安全风险。

论文的意义是：能力指标改善，并不保证安全性同步改善。风险可能出现于自训练、经验复用、工具构建与摄入、工作流聚合等不同环节。

但它没有把四条路径的全部风险证实为“最大化进化代理指标”这一个原因。其附录讨论的是潜在因素；记忆部分的共同原因明确写成假说。

> **§4**：“We hypothesize a unified cause for safety alignment decay and deployment-time reward hacking: agents over-relying on past experiences without critical reflection.”
>
> **对本分析的支撑**：这是对记忆风险的机制假说，不是四条路径统一因果的证明。[原文 v2](https://arxiv.org/html/2509.26354v2#S4)

论文也不只是把缓解留给未来。第 4 节与附录 E 已有初步研究：安全后训练、把记忆视为参考而非规则、工具摄入前提示安全判断，以及工作流聚合节点的安全提示。部分结果改善了安全指标，但未恢复原始安全水平。工具创建与复用的静态分析加模型复核，则包含尚未在该研究中验证的建议。**已做过的实验与提出的方案，不能混写成全部已验证，也不能混写成全部未开展。**

### 我的分析：把“二阶 Goodhart”当成待检验视角

我仍认为自进化要检查两层目标：单次任务的代理指标，以及进化过程用来选择下一版系统的代理指标。后一层可以叫“二阶 Goodhart”，但这是我的解释框架，不是 Misevolution 确立的四路径统一原因。

进化反馈更长，可能让风险更难发现；具体是否累积、由什么机制驱动，需要分别验证。训练数据、安全约束、记忆来源、工具权限与跨域复用，也可能产生不同风险，不能都用一个名字遮掉。

[GenericAgent](https://github.com/lsdefine/GenericAgent)及其[技术报告](https://arxiv.org/abs/2604.17091)关注复用技能、上下文信息密度与 token 效率。追踪同任务的 token 变化可以辅助观察学习，但**换一个指标不等于绕开 Goodhart**。只有在验收质量、任务难度、模型、缓存与运行配置相近时，下降才有可比较的意义。更短的输出也可能遗漏工作。

我希望进化仪表盘同时保留完成质量、安全失败、回归、成本与环境变化，而不只盯一个更便宜的分数。

## 过程支柱：程序闸门实际覆盖了哪里

### MOSS：源码级进化与多阶段验证

*MOSS: Self-Evolution through Source-Level Rewriting in Autonomous Agent Systems*（arXiv 2605.22794）把修复范围扩展到 Harness 源码，代码修改由外部编码 Agent 完成，阶段顺序和裁决由系统控制。

论文 §3.3 的七阶段主流程是 Locate → Plan → Plan-Review → Implement → Code-Review → Task-Evaluate → Verdict；构建与试运行在 §3.4 另有具体机制。临时 trial workers 构建候选镜像、回放失败批次，避免把未验证修改直接推入用户运行环境。

源码的价值在于：可以让宿主严格执行已经定义的谓词，而不只等模型读懂提示。可是**确定性执行不等于业务目标定义正确**。`output_file.stat().st_size > 0` 只证明文件非空，不证明完整、正确，也不证明覆盖需求。要检查完整性，还得定义必需字段、内容约束、引用、业务结果或外部状态。

这里的确定性也以检查实际运行、代码实现正确为前提。源码会有 bug，需求会变，外部服务会变；“不会因提示位置改变语义”不等于“长期永远可靠”。

#### 评分口径必须保留

MOSS v2 §4 的小型案例在 OpenClaw 与 DeepSeek V3.2 上，使用四个任务——两类任务的中英文变体，每任务三次试验。论文报告一次进化后 **mean grader score 从 0.2526 提升至 0.6100**；其任务通过阈值为 0.75。

> **摘要**：“On OpenClaw, MOSS lifts a four-task mean grader score from 0.25 to 0.61 in a single cycle ...”
>
> **对本分析的支撑**：改善的是这四个任务的平均评分，不是二元任务完成率从 25% 升到 61%。[§4 与 Table 2](https://arxiv.org/html/2605.22794v2#S4)

进化输入与进化后重新评分使用同批任务。因此，它展示了针对失败批次的修复能力，不能直接当跨任务泛化或生产可靠性的估计。

#### 提交后还有 gate，也有跨轮次比较

Implement 已把修改写成 git commit，此后仍有 Code-Review、Build/Trial、Task-Evaluate 与 Verdict。Verdict 使用 cross-iteration keypoint matrix，比较锁定的任务 keypoints；不是第二轮只能看“这次是否改对”。

部署又有两层控制：用户明确批准 promotion，以及容器替换后的健康探针与失败回滚。[§3.3—3.5](https://arxiv.org/html/2605.22794v2#S3.SS3)

所以，不能把 MOSS 描写成“只有行动中 gate，提交后完全没有”。更准确的评价是：它有计划、代码、任务、跨轮比较及部署控制，但检查覆盖依赖既定批次、keypoints 和健康谓词。**有跨轮检查，不保证发现所有长期结构性退化。**

### ClawMark：变化的外部世界，不是技能数量对数定律

*ClawMark: A Living-World Benchmark for Multi-Turn, Multi-Day, Multimodal Coworker Agents*（arXiv 2604.23781）包含 100 个任务，在模拟多日、多轮环境中测试 Agent。邮件、日历、文件、知识库等状态会在轮次间独立变化；评估器检查执行后的服务状态，而不只评最终文本。

在恰好三轮的 73 个任务子集中，七个受测模型有六个在 Day 2 下降，Qwen 3.6 Plus 上升；Day 3 部分模型恢复。这里的 Day 是任务世界中的模拟工作日，不是生产连续运行了实际几天。[v2 §6.1](https://arxiv.org/html/2604.23781v2#S6.SS1)

论文主结果基于每模型一次 sweep，未报告运行间方差。这个结果支持“环境更新后的适应是难点”，不能直接称为统计显著的普遍时间衰减规律。

**ClawMark 没有提供“技能数量 N 与准确率按 ln(N) 衰减”的实验或拟合。** 技能库膨胀可能增加检索误匹配，这是可以单独测试的工程假说；语义距离不均匀，本身也推不出对数律。本文不再把这个关系归给 ClawMark。

### AuthBench：先模拟权限需求，再审计；不是先宽权执行

*Do Coding Agents Understand Least-Privilege Authorization?*（AuthBench，arXiv 2605.14859）研究执行前的权限边界推断。其 Sufficiency-Tightness Decomposition 先前向模拟任务和工具链，生成覆盖导向策略，再审计每项授权的任务依据与敏感性。

> **§2.1**：“the model may inspect ... through read-only operations ... but may not modify the environment or execute the task.”
>
> **对本分析的支撑**：权限生成阶段可只读检查环境，不能真实执行任务。[原文](https://arxiv.org/html/2605.14859v1#S2.SS1)

构建 benchmark 的 oracle 标注使用过 `strace`，但那是安全参考解的标签采集，不是所提方法“让 Agent 拿宽权限跑完，再收紧”。把二者混淆，会把事前防护错写成事后补救。[§3.1、§7.1](https://arxiv.org/html/2605.14859v1#S7.SS1)

### 我的分析：三种机制服务不同边界

- MOSS：候选修改、试运行和部署是否通过既定验证。
- ClawMark：外部状态更新后，是否重新取证并正确行动。
- AuthBench：行动前的权限是否足够、又不过度。

它们能互补，但不是都在证明“约束有固定半衰期”。代码检查可以稳定执行，检查前提却可能失效；权限在任务变化后需要重评，状态缓存也可能过期。工程上应记录**前提与变化事件**，而不只按日历年龄认定失效。

## 评判支柱：后验状态、执行指引与独立证据

### Bayesian-Agent 实际提供的五动作

*Bayesian-Agent: Posterior-Guided Skill Evolution Across LLM Agent Harnesses*（arXiv 2606.08348）把技能作为证据对象，结合验证轨迹、上下文和先验维护后验状态，再选择技能动作。

v2 §3.5 给出 Explore、Patch、Split、Compress、Retire。默认策略包含样本数、重复失败、上下文异质性与后验估计等条件。比如 Compress 需要至少三条观察、成功后验估计不低于 0.72；它不是直接检验“后验区间已足够集中”。这些阈值是实现默认值，不是普遍认知规律。[§3.5](https://arxiv.org/html/2606.08348v2#S3.SS5)

论文在 SOP-Bench、Lifelong AgentBench 与 RealFin-Bench 上研究 Full 与 Incremental 模式。Incremental 使用已有验证记录，只修复失败任务；其修复成本与完整从零运行的总成本要分开看。

### 后验数字确实与模型提示分离，但文字指令不是免疫工具

> **§3.5**：“The model-facing context contains executable guardrails and repeated failure-mode patches, while posterior numbers remain in the audit state.”
>
> **对本分析的支撑**：论文保留可审计数字状态，对模型提供具体 guardrail 与失败修补指引，二者分离。[原文 v2](https://arxiv.org/html/2606.08348v2#S3.SS5)

这种设计避免让模型自行解释每一个概率数字，值得借鉴。但不能据此断言“73% 与 42% 在模型表征里没有稳定差异”，也不能断言文字动作不会被误读或漏做。论文没有证明这些普遍的认知机制与遵从保证。

更不能说这种分离单独切断自评正反馈环。**后验只能加工输入证据，不能自动把有偏证据变成正确标签。** 验证器是否独立、数据是否有选择偏差、上下文是否匹配，仍然承重。错误先验也可能造成偏差；论文 §3.2 明确讨论收缩估计的适用条件，并非贝叶斯方法普遍支配经验频率。

### 我的分析：给评分补证据，而不是取消评分

我更愿意把评判器设计成：结果、样本数、来源、失败模式、上下文和不确定性一起存。二元验收仍然有价值，标量均分也有明确用途；概率分布服务于后续决策，不替代底层事实验证。

[Harbor 的 Agent 集成文档](https://www.harborframework.com/docs/agents)展示了跨工具评估与运行结果记录的接口。轨迹互操作具有工程意义，但不能把 Harbor 支持某 Agent、某工具使用 ATIF，与所有公司采用同一标准等同。本文不以未逐项核对的采用名单证明三支柱。

交接损失、意图漂移和评判噪声也不应合并成一种熵。精确引用降低传递损失，代码 checker 执行明确谓词，证据模型记录不确定性——它们各自解决不同问题。

## 过程支柱的补充：行动前、中、后的治理

我保留“双门”的诊断语言：行动前明确意图、权限与委派范围；经验写入和复用前，检查证据、纠错解释与适用条件。这里按治理检查项讨论，不用没有公开来源的个人对话替它背书。

这不意味着已有系统只覆盖中间列。MOSS 已有部署批准与事后健康检查，AuthBench 本来就研究行动前权限，LangGraph 也有动态 interrupt、检查点与恢复。[官方 interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

LangGraph 的能力不是“任何已开始的外部动作都能无损中断”。暂停图执行、阻止下一次动作、撤销已发生副作用，是三件事；支付、发送和数据删除等外部结果，仍需独立权限与补偿设计。

因此，不能说“目前没有任何系统覆盖行动中监控和干预”。更窄的研究问题是：**如何在不同运行框架间一致地定义干预点、处理暂停与重放、保证副作用幂等，并审计人的批准？**

### 人的学习也是设计问题

执行外包可能减少试错；只看结果可能减少追问；默认接管可能削弱人的主动性。这些是值得测量的风险，不是人机协作必然导致人的单向退化。

一个可检验的设计是：在关键 PR 中呈现放弃的替代方案与理由，让人参与真正有风险的取舍。它可能帮助维护判断力，也可能只是增加阅读负担，效果需要观察，不能说“看过一次，判断力就得到维护”。

探索同样不能默认以最大信息增益为目标。获取敏感数据、扫描未知系统、扩大权限，可能有难以撤销的后果。但不确定不意味着完全无法事前评判：授权、隐私、资源上限与最小必要数据，可以先限制探索范围。这个问题提醒三支柱补入治理，不足以证明出现了完全独立的第四类定律。

### 共享知识库：项目能力与我的设计语言分开

[MindOS](https://github.com/GeminiLight/MindOS)当前公开说明强调本地 Markdown 知识库、MCP 与 Skills 桥接、原生会话及审计工作流等模块。早先关于 Canonical Markdown → Derived Sidecars → Evidence Pack 的三层描述，以及 Experience Compiler 是否未实现，不宜当成永久的当前产品事实。

我仍认为“原始记录—派生产物—可核验的证据包”是有用的知识治理设计，但这是本文的抽象。项目说明、实现状态与效果实验是不同证据层次。

## 工程工具链：相似模式不是收敛证明

[DataFlow](https://github.com/OpenDCAI/DataFlow)做数据准备与算子管线，[DataFlex](https://github.com/OpenDCAI/DataFlex)基于 LLaMA-Factory 提供数据选择、混合与重加权。当前 DataFlex README 明确，两项目独立、无代码依赖，通过标准数据格式连接。不能把它们写成必然一体化的轨迹训练闭环。

*Agent-World: Scaling Real-World Environment Synthesis for Evolving General Agent Intelligence*（arXiv 2604.18292）研究环境、任务合成与持续训练。[论文](https://arxiv.org/abs/2604.18292)

我看到的共同方向是：用可执行环境、结构化任务和验证信号组织数据生产。这有助于提出工具组合的假说，但“用了图”不等于方法严格同构，同场展示也不是行业已经收敛的证据。这里保留设计观察，不把它排在受控 benchmark 证据之上；项目 star 数与实现状态等动态信息，也不作为结论依据。

## 对原始框架的三个修正

### 修正 1：评判支柱增加证据状态

保留评分，同时记录样本、来源、上下文和不确定性。Bayesian-Agent 提供一种实现，不是唯一实现。可靠性首先取决于标签与验证过程，不只是更新公式。

### 修正 2：过程支柱增加前提重验

记录每个约束依赖什么：模型、任务、环境状态、数据版本、权限和运行层。时间可以触发复核，外部状态变化与任务切换往往更直接。“half-life”最多是提醒前提会变的比喻，本文没有量化普遍衰减规律。

### 修正 3：目标支柱同时检查进化目标和安全边界

能力、成本、安全与回归要共同观察。自进化也需权限、审核和回滚，不应把更高 benchmark 分数或更低 token 成本等同于更好系统。四条 misevolution 路径可被逐项诊断，不预设统一原因。

## 后续认知：持久化不是免责，自治时长不是交付量

会后的思考让我更重视三条跨支柱约束。以下是我的工程延伸，不归给大会发言，也不声称上述论文已经验证其全部效果。

首先，给实现设置**复杂度与副作用预算**：新增状态、依赖、兼容路径和外部影响，都应有明确价值与验证。更快的实现只消除了部分生成摩擦，不能抵消未来维护成本。

其次，给无人值守与并行工作设置**未验收在制品上限**。持续运行可以增加候选产物，也可能增加验证债务；若审查、测试与业务验收跟不上，就先降并行、缩切片，避免未确认结果不断喂给下游。衡量的是已验收的可信变化，不是运行小时数。

最后，把恢复承诺分层：事实日志、当前模型上下文与执行现场不是同一种状态。系统能够重放聊天，不意味着能够恢复进程，更不意味着外部写操作可以安全重做。经验持久化前要保留证据、适用条件和撤销路径；上下文压缩也不能把概率性摘要升级为唯一事实。

经验复用还需要一条发布边界：保留成功、失败与修正的证据，候选带来源、适用条件和复核触发；通过独立 Eval、版本化与适用批准后，才成为生产 Skill 或默认规则，上线后能撤回。后验更新加工证据，经验发布改变未来行为，二者不能用同一个“学到了”按钮代替。

这些约束共同改变了我的问题表述：不只问“如何让 Agent 继续推进”，还要问**什么值得推进、积压多少就停止、恢复后怎样确认没有重复或越权**。

## 主要证据入口

## 推断与未证实部分

三支柱的木桶结构、二阶 Goodhart、约束前提观测层、人类学习节点，以及工具组合的收敛方向，都是我的分析。多项研究给它们提供比较材料，但独立来源不能消除我的选择偏差，类比也不是确认性验证。

仍待研究的是：干预如何跨框架协作；验证者与 ground truth 如何持续校准；不同任务如何量化风险和成本；哪些补偿组件可以随能力提升退出，哪些治理职责必须持续存在。
