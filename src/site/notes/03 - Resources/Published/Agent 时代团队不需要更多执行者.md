## 核心观点

- AI agent 正在压缩"执行层"的价值空间；我主张淘汰的是不做判断的工作模式，不是把某类人判为没有价值
- 在任务可拆分、上下文可获得、结果可验证的场景里，团队的最小交付单元可以从"1 个 lead + N 个执行者"演变为"1 个判断者 + agent 集群"
- 管理者"不如我自己做"的直觉可能被上下文优势扭曲，不能据此停止委派和培养
- 真正的杠杆不是你一个人带一群 agent，而是找到能独立驱动 agent 的人
- 判断力不是抽象的"要有 ownership"，它有具体的表现形态：导航、裁判、断路

## 一个技术管理者的日常困境

你给团队布置了一个明确的技术方案，不存在模糊地带。得到的反馈是："这样可能有问题，你确认一下所有细节。"

你的第一反应是：这些细节不正是你应该自己验证、然后给我结论的吗？第二反应是：算了，我用 agent 做可能更快。

如果你带过团队，这个场景大概率不陌生。执行力很强、能吃苦、遇到技术难点能一个个啃下来——但工作模式是：你告诉我每个细节，我来实现。遇到不确定性，默认上抛而不是自己闭环。

这类工程师不是能力差，而是把自己定位成了"指令的接收端"。在 AI agent 已经能承担不少边界明确、可验证的实现任务的今天，这种定位还有多少价值？明确指令不等于可靠交付，但只接收指令也越来越难成为工程师的价值中心。

## 执行层的价值正在被压缩

这不是一个关于个人能力高低的判断，而是我对成本结构变化的判断。它是否成立，要看同等质量下的完整交付成本，而不是只看生成速度。

设想一个常见的比较：工程师花三天写代码、调试、部署，agent 三小时完成初版。这两个口径不能直接相减。初版后还有 review、返工、集成、部署和维护；agent 的 token 费用也不是人的注意力与责任成本。只有把这些都计入，才能判断这次委派到底省了什么。

当部分实现工作的边际成本下降时，"能执行"就不再像过去那样稀缺。我关心的是工程师把省下来的注意力放到哪里：少盯机械性实现，多思考架构、约束和验收。不是 agent 让架构突然变重要了，而是实现变快之后，架构原本的重要性更容易被看见。

Sia Partners 2026 年的咨询分析转述了多数组织 5-10%、顶尖组织 20-60% 的生产力增益，并把差距联系到工作流和治理结构。这里的百分比是该文的报告口径，不是我独立核验的普遍增益，也不是控制模型、任务和组织条件后的因果实验。它支持的是一个值得验证的管理方向：别只买工具，要重新审视工作流。

研究时效也不能忽略。METR 在 2026-02-24 的更新中认为，当时的工具更可能让开发者获得加速；但参与者和任务的选择偏差，使新数据无法可靠量化增益。这既不能支持"AI 总会更慢"，也不能支持"执行成本已经趋近于零"。我的判断是：在实现被明显加速的任务里，决策、验证和集成更容易成为瓶颈。

这意味着团队中"你告诉我细节我再动手"的工作模式，越来越多地落在 agent 能承担的区间里。不是这些人变差了，而是只提供实现、不承担验证和判断的价值空间正在被压缩。

## 团队的最小单元正在重新定义

传统的技术团队结构是金字塔形的：一个技术负责人定方向，几个主管分模块，每个主管带几个执行者。信息从上往下流，代码从下往上交。

在 agentic engineering 的语境下，这个结构正在被压扁。LeadDev 2026 年 4 月的文章直接问了一个问题：AI 时代，团队规模还重要吗？

我的观察是，在边界清楚、可独立验收的任务上，团队的最小交付单元可以从"1 个 lead + N 个执行者"演变为"1 个高 ownership 的人 + agent 集群"。这不意味着复杂系统只需一个人，也不意味着安全、运维和跨团队协作可以消失。这个"人"不是传统意义上的 leader——他不需要带人、不需要做绩效、不需要开周会。他需要的是：能定义问题、能在模糊地带做判断、能对结果负责。

而那些把自己定位成"指令接收端"的工程师，问题不是技术能力不够，而是没有把"在不确定性中做判断并承担结果"当成自己的职责。每次遇到模糊地带，默认行为是上抛——让上级来确认、来拍板、来承担判断错误的风险。

在没有 agent 的时代，这种模式更容易被接受，因为执行力本身就足以贡献价值。当 agent 能承担更多实现时，判断力就成了更高的准入要求。执行能力、领域知识和沟通仍然重要；问题是，不能再把判断全部留给上级。

## "不如我自己做"是一个危险的陷阱

意识到这一点之后，很多管理者的第一反应是：既然 agent 能执行，我又能做判断，那我一个人 + agent 不就够了？

这个想法很自然，但很危险。

管理者觉得 agent 比团队成员快，可能有一个隐藏的原因：你给 agent 开放了文档、spec 和代码库，却还在靠口述向成员交代背景。Agent 不天然拥有上下文；人也可以直接读文档。若两边的信息入口不同，比较就先被扭曲了。

你比较的可能不只是人和 AI 的能力差距，也包括文档驱动和口述驱动的效率差距。先让成员获得同等上下文，再判断差距，否则容易掉进效率幻觉。

更危险的是，这个陷阱可能自我强化：你觉得"不如自己做"→ 减少委派 → 团队成员得不到锻炼 → 能力差距进一步拉大 → 更加"不如自己做"。Russinovich 和 Hanselman 关于"senior boost / junior drag"的讨论提醒了类似风险：如果组织只看资深成员的短期增益，停止招聘和培养新人，就可能损害未来的人才供给。这是组织风险，不是"五年后必然没有 senior"的预测。

还有一个容易忽略的点：agent 可以挑战你的假设，也可以比较方案，但不能把它会质疑当成独立纠错的保证。同一份上下文、同一套目标和你的反馈，可能让它沿着你的偏好越走越快。团队成员的"笨问题"有时候恰恰带来了另一份经验和利益视角。如果你把这些人际纠错都替换成 agent，又没有独立验证，就可能更快地走向错误的方向。

所以真正的杠杆不是"我一个人 + agent"，而是找到 2-3 个同样能驱动 agent 的人。每个人都是"判断者 + agent 集群"的节点，而不是你一个人变成单点故障。

这还需要一个容量约束：团队不能把 Agent 的产出量当成已交付量。我会明确每项变化的验收责任人，观察未验收产物的数量、年龄、风险和下游依赖；积压超过当前验证能力时，限制新任务与并行度，先还验证债务。无人值守运行延长的是执行窗口，不会自动延长人的审查带宽。可靠自动化可以扩展验证能力，但业务裁决和关键取舍仍要留出专注时间。这是运行管理建议，不是“所有团队只需两三人”的人员公式。

还要保护独立定义问题、形成判断与找反例的时间，再让 Agent 帮助检索、比较和质疑。若系统会主动发现机会、追加任务，收益还应扣回筛选、确认、纠错与收尾的注意力负担；多完成任务不自动等于替人省心。必要审批和真实失败不能为“少打扰”被隐藏。

## 判断力不是抽象的——它有具体的形态

说"团队需要有判断力的人"太笼统了。判断力在 agent 协作中至少有三种具体形态：

**导航者**：决定探索方向。当 agent 可以大量搜索解空间时，人的价值不只在于亲自搜索，而在于约束搜索范围。"不要往这个方向走了，换一条路"——agent 可以提出这个建议，但全局目标、业务取舍和授权边界需要有人维护并承担决策责任。导航者的核心工作是约束解空间，而好的架构设计本质上就是一种约束。

**裁判**：判断结果是否正确、是否有意义。Agent 可以结合业务上下文评估方案，但没有被提供的信息不会凭空出现。一个技术上能跑的微服务拆分方案，如果忽略团队只有三个人、下个季度要砍预算、流量根本不需要拆分，就仍然不合理。发现与论证是两件事：找到一个数学构造不等于完成证明，生成一段能运行的代码也不等于证明它应该存在。裁判要借助测试、业务证据和 agent 的分析完成验收，而不是假设某一方天然能判断一切。

**断路器**：识别 agent 陷入死胡同并主动中断。长上下文中的既有输出可能形成锚定和叙事惯性，但并非每个 session 都必然如此。Agent 也能借助新证据、工具反馈或重设问题修正方向。人的职责是设置停止条件、检查是否真的进步，在反复重试却没有新证据时主动断路，而不是被动等它失败。

回到开头的场景：那类工程师缺的不是执行力（探索者角色），而是导航和断路的能力。不敢自己判断方向，不敢在不确定性中做决策，不敢说"我验证了，这条路走不通，建议换方案"。

## 怎么办：训练窗口、招聘标准、组织演进

对于现有团队中的执行型成员，核心是重新定义交互契约：

**关掉"把判断责任原样上抛"的通道，打开"带证据、结论和建议来升级"的通道。** 在成员有权限、有信息、试错可控的范围内，不替他做判断，要求他先验证、先给结论和建议方案，你只做最终拍板。判断错了复盘就好，不因合理试错追责——但不做判断不行。重大风险、权限不足、信息缺口和不可逆动作必须保留及时升级通道，不能要求为了显得独立而硬做。

我会给一个明确的训练窗口，例如 2-3 个月。这是我的管理方案，不是研究得出的通用期限。如果给足上下文、授权、反馈和训练后，仍无法在约定范围内闭环，就应认真讨论岗位匹配；不能跳过这些条件，把合理求助直接算成不胜任。

对于招聘，筛选标准需要从"能不能干活"转向"能不能在模糊地带做判断并承担结果"。一个有效的评估方式是：给候选人一个真实项目场景和一个相对较弱的模型，观察他如何弥补模型的不足——任务分解、质量判断、方向决策，这些才是 agentic engineering 时代的核心能力。

对于组织演进，方向是：

- Leader 的职责从逐项代做判断，转向"技术判断 + 质量护栏 + 使能"，培养新人仍是使能的一部分
- 组边界变软，行政归属保留，项目分配按需组成临时战斗单元
- 强 leader 的判断力跨组辐射，不局限于自己的 2-3 个人

## 不是淘汰人，是淘汰一种工作模式

写到这里，我想澄清一点：这篇文章不是在说"能力一般的人应该被淘汰"。

被淘汰的不是人，而是"你告诉我做什么我就做什么"这种工作模式。一个愿意转变的人，完全可以从执行者成长为判断者——前提是他意识到这个转变的必要性，并且愿意承受转变过程中的不适。

真正的风险不在于团队里有执行型的人，而在于整个团队都是执行型的人，只有你一个人在做判断。那样的话，你不是在放大一个团队，而是在操作一群"人形 agent"：判断仍堵在你这里，委派并没有形成真正的杠杆。

Agent 时代对团队的要求很简单：每个人都应该是一个能独立做判断的节点，而不是一个等待指令的终端。
