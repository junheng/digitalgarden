## 问题缘起

2026 年初，我做了一次 multi-agent 编码实验。第一次用 Waterfall 模式——分析 Agent → 分派 Agent → 执行 Agent → 审查 Agent。结果消耗了数十亿 token，几乎没有推进。Agent 们产出了越来越长的 handoff 文档，大量 token 烧在交接上，而非实际产出。这是我的单次工程经历，不是不同架构的受控对比。

于是切换到 Loop 模式——纵切迭代，每次推进一个完整切片。推进速度改善，但新问题出现：mock 实现、临时测试桩、模式匹配式的代码被保留下来，逐步加大后续迭代成本。

这提醒我不能只看单个 Agent 的输出。局部工作看起来合理，系统仍可能停滞或漂移；能力、信息、流程和验收都可能参与失效。

本文提出一个诊断框架：**指引 Agent 行为的三个维度——目标设定、过程设计、评判反馈——像木桶的三块板。** 这个比喻帮助我寻找短板，但它不是关于三者严格不可替代的定理，也不声称覆盖了授权、隐私、责任与人类学习等全部维度。

## 三支柱框架

### 目标支柱——代理指标的递归风险

复杂知识工作的目标通常不能被一组指标完整表达。我们借助代理指标（proxy metric）衡量进展；当指标与真实目的有缝隙，优化过程可能获得高分却损害实际目标。这种投机利用（exploit）不必依赖 Agent 的主观恶意。

加审查、加验证、加约束，可能增加新的可投机表面，但**并非所有防线都是另一个可被同样方式操纵的分数**。最小权限、硬性资源边界与独立留出测试，可以改变系统可采取的行动，而不只是改写评分文本。

Tian Pan 的 [Goodhart 博客](https://tianpan.co/blog/2026/04/20/goodharts-law-ai-agents-eval-gaming)汇总了形式化研究和投机案例。他是这些研究的转述者，不应把几何模型或 RL 实验归给他本人。本文把该博客作为问题入口，不再用其中转述的百分比证明三支柱框架；未经逐一追溯原论文的数字，不承担这里的定量论证。

我的工程问题是：**这个分数是否真的对应我们要的结果？防止投机的检查，是否有独立证据和真实执行边界？**

### 过程支柱——控制有效变化，而不是追赶模型智力

Ashby 的必要多样性定律（Law of Requisite Variety）讨论调节器的响应、扰动与允许结果之间的多样性关系。[原书第 11 章](https://ashby.info/Ashby-Introduction-to-Cybernetics.pdf)

把它迁移到 Agent 设计，我得到的启示是：控制能力要匹配**任务中需要处理的有效变化**。但这不是“模型越聪明，Harness 代码量就必须同比增长”。限制工具、授权范围与数据面，衰减扰动、明确不变量，都能减少需要控制的变化。

简单规则可能不够，复杂规则也可能成为第二个需要维护的系统；两者都不是必然结局。工程目标是找足够有效、可测量、可维护的控制组合，而不是把复杂度增长当宿命。

Casserini 等人的 *Beyond the 'Diff': Addressing Agentic Entropy in Agentic Software Development*（arXiv 2604.16323）提供了另一个有用概念。

> **摘要**：“the accumulating divergence between agentic actions and architectural intent. We term this process agentic entropy: a systemic drift ...”
>
> **对本分析的支撑**：agentic entropy 指 Agent 行动与架构意图的累积偏离，不是多跳交接必然造成的香农信息损失。[原文](https://arxiv.org/abs/2604.16323)

这是一篇过程可解释性的立场论文。它提出以意图层面的观测补充 code diff，不能被当成“完美 Agent 交接也必然丢信息”的数学证明。

MAST 的 *Why Do Multi-Agent LLM Systems Fail?*（Cemri 等，arXiv 2503.13657）则用跨七个框架、1600 多条标注轨迹建立失败分类。

> **摘要**：“14 unique modes, clustered into 3 categories: (i) system design issues, (ii) inter-agent misalignment, and (iii) task verification.”
>
> **对本分析的支撑**：原分类是系统设计问题、Agent 间失配与任务验证；不是“规范失效、协调死锁、记忆污染”。[原文](https://arxiv.org/abs/2503.13657)

MAST 的三类也不是本文三个支柱的同义词。我可以把具体失败拿来对照框架，但不能替换论文分类后，再给替换后的类别挂上百分比。原先的 42%/37%/21% 组合不保留。

### 评判支柱——独立证据比角色数量更重要

开放式知识工作的评判可能很难，但不能一概说“评判与创作总是同样难”。已有产物、测试、实际状态和需求约束，常能降低部分验证的成本；对架构取舍、业务意图与长期维护性，仍需要更强判断。

用一个 Agent 审查另一个 Agent，能增加检查，但不会自动保证独立性。审查者也可能继承同一错误规格、共享模型盲区，或者只核对生成者的自我总结。

MAST 把任务验证列为独立失败类别，提醒我把终止与验收内建到工作流。**本文的进一步建议**是：区分“输出声称完成”“产物检查通过”“外部状态确实改变”，并让评判器接受独立校准，而不是只增加审查角色。

### 为什么“综合使用就好”还不够

三个维度会相互影响：更多约束可能减少探索，也可能帮助探索聚焦；更多 review 可能延长反馈，也可能阻止高成本返工。影响的方向取决于约束内容、风险与执行方式，不是一条单向的因果链。

工程挑战是：在给定任务和模型下，找出最轻量的组合，测量成功率、风险、成本与延迟。木桶比喻是诊断起点，不替代测量。

## 两种值得区分的失效模式

### 失效模式 1：交接丢失与架构意图漂移

Waterfall 中，分析 → 分派 → 执行 → 审查 → Human，每个 handoff 边界都可能漏掉设计理由、替代方案和尚未解决的约束。反复重写摘要，也可能把假设固化成事实。

但这里有两个不同问题：

- **交接损失**：原始信息是否在传递、摘要与检索时遗漏。
- **agentic entropy**：行动是否逐渐偏离架构意图，即使信息都保存了仍可能发生。

共享原件、精确引用、持久产物、可回读决策日志，可以降低交接损失；它们不能自动防止对意图的误解。反过来，减少 Agent 数量也不必然改善质量：专业分工与独立验收可能有收益。

因此，我不再把自然语言交接等同于不可逆失真，也不据 Shannon 理论断言任何多跳结构必然失败。要检查的是**哪些信息被删了、哪些决策偏离了、哪些边界没有验证**。

### 失效模式 2：局部优化累积

Loop 中，mock、临时测试桩和看似匹配的实现可能逐轮保留下来。如果验收只看本轮完成率，不检查系统不变量，这些妥协可能形成后续负担。

我观察到三个压力来源：

1. **任务完成压力**——评估本次完成，忽略长期维护性。
2. **信息压力**——上下文或检索不足时，难以检查全局依赖。
3. **后果反馈不足**——短会话看不到后续维护成本，错误经验也可能被复用。

这是风险机制的归纳，不是“贪婪算法必然腐化”的证明。真实 Agent 工作流不等于一个已形式化的贪婪算法，局部最优是否妨碍全局目标也依赖任务结构。

同样，人类在类似激励下也可能做局部优化，但并非必然如此。正确的改进是把长期约束、维护反馈和独立回归接入迭代，而不是把失败归结为任何参与者都无法改变的命运。

## 后续修正：把短板诊断落实为运行预算

后续实践让我把框架向三个更具体的检查点推进。它们是工程建议，不是由三支柱推出的定理。

- **复杂度与副作用预算**：完成一个功能之外，还要检查新增抽象、依赖、状态、迁移和受影响消费者。少写代码不自动等于少复杂度；应要求长期负担有当前、可验证的价值。
- **验证债务与在制品上限**：当未验收产出持续增加，应限制新任务和并行度，优先清理验收积压。不能只给 Agent 更多执行时间，让未经核实的代码与结论继续成为下游输入。统计要区分风险和验收工作量，不把代码行数当统一债务单位。
- **状态分层与恢复承诺**：事实日志保存发生过什么，上下文表面保存模型现在看什么，执行现场决定还能够从哪里继续。原件可回读不等于副作用可重放；恢复时要核对当前授权、目标和外部状态。

在此之外，我会给经验复用增加发布边界：成功、失败和修正先成为带来源、适用条件的候选，不直接改写生产 Skill 或默认规则；经过版本化、独立 Eval 与适用的批准后再发布，出现偏差可撤回。证据记录与行为定义有不同权威，不能用一句“学到了”合并。持续运行也要保留最新目标、暂停项和额度，把执行权限与完成判定依据分开。

这不是简单增加第四、第五根柱子，而是让目标、过程与评判共同约束真实运行。框架的价值应体现在可执行的预算、停止条件和验收证据上，而不只在架构图上。

## 未解决的问题

1. **三个维度的最低可行水平如何定义？** 应以任务风险、真实验收和资源成本描述，而不只事后说“板太短”。
2. **持久会话如何同时保留经验与撤销错误经验？** 持久化可能减少交接损失，也可能固化偏见；两面都要测。
3. **提高反馈密度何时有效？** 快速反馈可能纠偏，也可能放大有偏指标，关键是质量与独立性。
4. **如何减少需要控制的变化？** 限制授权与工具面，可能比增加更多提示更有效；但过度限制也会让任务不可完成。
5. **框架遗漏了什么？** 组织责任、隐私、人类学习与外部副作用，不应因为难归类就被排除。

## 下一步：从诊断语言到工程工具

三支柱帮助我组织问题，但不提供自动治疗方案。在后续[大会文](https://nexus.sigmoid.cc/AgenticAICon%202026%20%E2%80%94%20%E4%B8%89%E6%94%AF%E6%9F%B1%E6%A1%86%E6%9E%B6%E7%9A%84%E7%8B%AC%E7%AB%8B%E9%AA%8C%E8%AF%81%E4%B8%8E%E5%B7%A5%E5%85%B7%E5%8C%96/)中，我把 MOSS、AuthBench、ClawMark、Bayesian-Agent 与 Misevolution 放到这个框架旁边比较：看它们实际解决什么，也看它们迫使原框架修正什么。

它们不是为本文框架设计的确认实验。工具有相似性，不等于同一个问题已经被解决；gate 有覆盖，也不等于长期治理已经完备。

## 证据来源

- [Casserini 等，Beyond the 'Diff'，arXiv 2604.16323](https://arxiv.org/abs/2604.16323)：过程可解释性的立场论文，概念与工程建议不能等同效果验证。
- [Cemri 等，Why Do Multi-Agent LLM Systems Fail?，arXiv 2503.13657 v3](https://arxiv.org/abs/2503.13657v3)：分类与标注轨迹支持受测系统的失败分析，不保证覆盖所有框架与新模型。
- [Ashby，An Introduction to Cybernetics，第 11 章](https://ashby.info/Ashby-Introduction-to-Cybernetics.pdf)：控制论概念；向 Agent Harness 的映射属于本文推断。
- [Tian Pan，Goodhart 博客](https://tianpan.co/blog/2026/04/20/goodharts-law-ai-agents-eval-gaming)：二手来源，不代替原始论文的数字与方法。

## 推断与未证实部分

三支柱本身、木桶比喻、反馈密度的权衡，以及这些维度之间的映射，都是我的分析。它们可能遗漏维度，也可能存在不同支柱间的工程补偿。模型能力提升既可能扩大控制面，也可能让部分补偿组件退出；不能提前规定 Harness 必然越来越厚。
