## 一个被忽略的设计问题

讨论 Agent 系统设计时，大多数对话集中在「该加什么」——加 planner、加 evaluator、加 memory、加 RAG。框架在膨胀，组件在堆积，架构图越来越像微服务拓扑。

很少有人问反向的问题：**哪些组件将来该被拆掉，哪些职责不该？** 不是「这个组件有没有用」——有用的组件太多了。问题是，在它被创建之前，设计者是否知道它的存在前提是什么，什么证据允许它退出？

我把这两种设计姿态称为 Build to Delete 和 Build to Last。但组件不是非黑即白的两类：同一个 evaluator，可以既帮助模型纠错，又承担独立验收。能削减前一种负担，不代表后一种责任也消失了。

Anthropic 的长运行应用 Harness 案例，提供了一个值得拆开看的起点。

## Anthropic 拆掉了什么

在「Harness Design for Long-Running Apps」中，Prithvi Rajasekaran 记录了随着模型与任务变化而裁剪 Harness 的过程。这里不是一次从 Opus 4.5 升级到 4.6 就同时拆掉三个组件：**Context Reset 在 Opus 4.5 阶段已经移除；升级到 4.6 后，作者又移除了 Sprint 分解，并把 Evaluator 从逐 Sprint 检查改为整轮构建后的 QA。**

这不只是用更好的设计替代旧设计。有些安排确实被移除了，因为它们原来补偿的能力缺口，在该模型和任务上不再同样承重。

| 安排 | 原来补偿的问题 | 原文中的变化与边界 |
|------|----------------|--------------------|
| Context Reset | 早期 Sonnet 4.5 的 context anxiety，使长任务过早收尾 | Opus 4.5 大幅缓解该行为后移除 reset，使用自动 compaction；不是所有上下文风险消失 |
| Sprint 分解 | 通过分块保持复杂构建的连贯性 | Opus 4.6 的案例中，Builder 能在没有 Sprint 分解的情况下连续构建两小时以上；不代表任意任务都不再需要分解 |
| 逐 Sprint Evaluator | 分阶段发现实现缺口、反馈修复 | 改为整轮构建后的 QA；Planner 与 Evaluator 保留，边界任务上的检查仍有价值 |

原文的两组时间和费用也必须放回各自任务：V1 的 **retro game maker** 使用 Opus 4.5，完整 Harness 运行 6 小时、费用 $200；V2 的 **DAW** 使用 Opus 4.6，运行 3 小时 50 分、费用 $124.70。任务、模型、提示和系统结构都不同，**不能据此声称同一任务从 6 小时/$200 降到了约 3.8 小时/$125，更不能把差异因果归结为「只是跑得更少」。**

真正值得借鉴的方法是：**逐个移除，检查影响。** 作者先大幅裁剪，发现难以复现原效果，也难判断哪些组件承重，才转向一次移除一个组件并审阅结果。Planner 移除后，Generator 缩小了产品范围，所以保留；Evaluator 调整了检查粒度，但没有被整体删除。DAW 案例仍经历了 QA 发现缺口、Builder 修复、再验收的多轮循环——「整轮结束后检查」不等于「整个任务永远只检查一次」。

我的提炼是：不只问「还能加什么」，也问**「我可以停止做什么，凭什么证明停掉后仍然合格」**。

## 模型是大脑，Harness 是手脚——也承担责任边界

要回答这个问题，需要先理解模型和 Harness 的分工。

在常见的工具调用系统里，模型生成输出和行动提议；真正写文件、调用 API、接收事件、保存跨会话状态的是运行环境。模型能力变强，可以改变怎样规划行动，但不会自动替代这些外部机制。「大脑与手脚」是帮助理解这种分工的比喻，不是对所有模型架构的本体论断言。

Harness 提供的至少有三个功能维度：

| | 能力补偿 | 行动接口 | 长期治理与可靠性 |
|---|---|---|---|
| **做什么** | 帮助当前模型规划、拆解、纠错 | 连接持久化、I/O、工具调用、消息路由 | 落实授权、权限、隐私、审计、幂等、外部状态核验与独立验收 |
| **存在原因** | 当前模型在特定任务上的能力缺口 | 模型需要运行环境才能影响外部世界 | 系统必须对人、组织和现实风险负责 |
| **随模型升级** | 重测存在前提，可减弱或退出 | 实现可以换，接口职责通常仍在 | 不能仅凭模型变强就删除责任边界 |
| **设计姿态** | **Build to Delete**：可拆卸、有退出条件 | **Build to Last**：稳定契约、可替换实现 | **Build to Last**：持续承重、可审计地演化 |

这是功能分类，不是给整个组件贴一个永久标签。规划也可能包含范围批准，约束也可能落实隐私政策，评估也可能是独立验收。把这些一概归入「模型不够聪明」，就会把应该保留的责任一起拆掉。

## 能力补偿层：为退出设计，而不是预言过期

能力补偿层的安排编码了「模型在这个任务上还做不好 X」的假设。规划、任务分解、逐步骤纠错、某些提示技巧——如果主要用于弥补当前能力缺口，就应该在模型或任务变化后重新测试。

这不意味着每次升级都应删除，也不意味着它们有统一半衰期。模型变强的同时，任务可能更长、更复杂；旧任务上能卸掉的支架，在新任务上仍可能承重。

值得强调的是**规模不是判断标准**。一个三行的约束 prompt 和一个多 Agent 编排管线——如果都只用于补偿推理局限——都应有退出条件。一个复杂系统也可以被设计成 Build to Delete，前提是职责可分离，移除后的效果能被验证。

这要求设计者从一开始就按「可拆卸」构建：模块化、松耦合、显式状态契约，每个组件能独立测试，也能独立移除而不波及其他部分。文件是一种可回读的交接方式，但不是松耦合的唯一途径；共享内存、数据库或消息同样可以有清晰契约。关键不是选哪个媒介，而是依赖是否显式、状态是否可恢复、替换是否可验证。

不是因为组件不重要——恰恰因为你需要知道它什么时候不再重要。

## 按失败类型持续校准，不按模型版本整体折旧

后来我进一步修正了“组件价值只由模型缺陷定义”的前提：Harness 也可能放大可靠性、提供独立证据，或落实组织的治理要求。模型在某些样本上已经会做，不代表在目标任务分布上稳定；但这也**不证明某个验证器永远有效、永远不能删除**。要保留的是必要职责，具体实现与检查频次仍应重测。

因此，组件审计不只比较一个平均成功分。我会按格式、感知、规划、事实、状态与权限等失败类型，记录“有组件／无组件”的差异、回归和成本。模型版本变化是一种重测触发，不是所有组件的统一到期日；优先测已变化的能力，也保留其他关键类别的回归检查。

同样，Evaluator 不能只因独立于 Generator 就默认可靠。反馈若误判或只引导局部补丁，继续修复可能扩大偏离。应检查反馈是否准确、已通过的不变量是否仍成立，并设置无进展停止条件。确定性检查适合明确谓词，也可能因谓词错误或覆盖不足而给出虚假信心。

“可拆卸”也不能只靠模块化：卸载要清理监听、计时器、注册与临时资源；替换要处理持久状态迁移，并留下可回读证据。这里的可逆指组件生命周期与切换准备，不代表已发送消息、已付款或已删数据能够自动撤销。

这些是我的工程审计主张，不是关于所有模型、所有 Harness 的普遍定律。重点从“模型变强就做减法”，转向**按失败类型、职责和风险持续校准**。

## 行动接口层：为什么 Build to Last

行动接口连接模型与外部世界。现实系统有文件、数据库、API、传感器和用户事件，这些功能不会仅因推理能力提高就自动消失。

持久化机制、消息管道、外部工具调用协议——稳定的是这些职责，不必是今天这份实现。不是「绝不拆」，而是**拆了之后往往需要保留功能等价的能力**。

这层组件的设计姿态是稳定接口。稳定不意味着复杂——恰恰相反，行动接口最有价值的属性是简单、可测试和可替换。

[Script-as-Pipeline — Agent 管线中的脚本节点设计模式](https://nexus.sigmoid.cc/Script-as-Pipeline%20—%20Agent%20管线中的脚本节点设计模式/) 讨论的 stdout，是一种通信接口。它本身不会把模型对文本的理解变成确定性控制：让 agent 解读输出再选分支，仍依赖模型；让宿主按 schema 解析控制字段、检查路由 allowlist 和权限，再执行分支，才是程序落实的控制流。

可长期保留的是通信与控制契约，不是某个 emoji、某段 prompt，甚至不必是 stdout 这个具体通道。接口质量和模型理解力都需要测试，不能把其中一个假定为与另一个完全无关。

## 长期治理层：聪明不等于有权，也不等于验收通过

这一层是二分法容易漏掉的部分。

授权确认、最小权限、隐私边界、审计记录、幂等处理、外部状态核验和独立验收，不只是因为模型容易犯错。它们也在回答：谁允许系统做这件事？哪些数据能出去？重试会不会重复扣费？交付到底有没有达到约定标准？出了问题能不能追溯？

模型更聪明，可能减少需要人逐步纠偏的次数，却不会因此自动获得权限，也不会取消组织的责任。治理机制可以简化、自动化或迁移，但削减它们需要单独的风险与授权依据，不是一次模型升级就够了。

Evaluator 是典型的混合组件。逐步指导 Generator 纠错，是可能被削减的能力补偿；按独立证据确认成果、检查用户验收标准，则仍可能承重。分开一个 QA agent 也不自动保证统计独立或判断正确，它自己的标准、覆盖和校准仍需检验。

Anthropic 的案例说明检查粒度可以改变，且末端 QA 仍发现了核心交互缺口。它不是删除所有评估的证据。我把授权、隐私等另列为长期治理，是在此基础上的设计判断，不是声称这篇工程报告已经验证了完整生产治理方案。

## Build to Last 也会重建——但要算总成本

「Last」不意味着实现永远不变。接口、依赖、工具和需求都可能变化，代码生成也可能降低某些实现的初稿成本。**但这不等于已经证明构建成本普遍按指数下降。** 有限适配器上的快速生成，不能外推到复杂系统的迁移与长期维护。

即使某个组件花 $50 就能生成，也不能直接得出「不值得维护两年，重建更便宜」。这里的 $50 是假设的初稿成本，不是案例数据。还要算数据与状态迁移、兼容性处理、集成验证、安全审查、独立验收、切换和回滚准备，以及切换后观察的成本。旧实现有已知限制，新实现也有新的未知风险。

所以，行动接口层的策略不是「便宜了就毫不犹豫地重写」，而是：**保持简单和可替换，在覆盖迁移、验证与风险的重建总成本低于继续维护的预期成本时，再选择替换。** 耐久性与可替换性不是互相取消，稳定契约让替换更安全。

## 对设计者的意义

在动手设计一个 Agent 系统前，不只问「它补偿思维缺陷，还是填补行动缺口」，还要问：**它是否承担必须持续保留的治理与验收职责？**

- **能力补偿** → Build to Delete。模块化，独立测试，明确退出条件。允许它在重测后消失，不预设哪次升级一定能删除。
- **行动接口** → Build to Last，但保持可替换。稳定的不是实现，是功能与契约；重建要算总成本。
- **长期治理** → Build to Last，也允许演化。授权、权限、隐私、审计、幂等和独立验收不能仅因模型变强就撤下。
- **混合组件** → 按职责拆开判断。先保留承重部分，再测试哪些补偿与执行频次可以减少。

两种姿态的混淆是 Agent 系统的隐性成本。把能力补偿当成永久架构，结果是 Harness 越来越厚，却没人能说清哪些部分还在承重。把行动接口和治理当成临时代码，结果是模型跑得更快，手脚却未经验证、权限边界也随之松动。

## Harness 审计：先查职责，再做减法

传统的 Harness 审计只问：这个组件还有用吗？我更愿意把它展开成四个问题：

1. 这个组件承担哪些职责：能力补偿、行动接口、治理与验收，还是混合？
2. 对能力补偿——当前模型在相同或可比任务上的测试，是否支持它退出？
3. 对接口与治理——替换后是否保留契约、权限边界、审计和验收能力？
4. 对重建——纳入迁移、验证、切换和回滚后，总成本与风险是否真的更低？

三种决策：**拆除、保留、重建。** 对应三件不同的事，应该按职责和证据作出，而不是按组件名字作出。

Anthropic 移除 Sprint 分解时做的是拆除；保留 Planner 与末端 Evaluator 时做的是保留。V1 中的 Sprint Contract 也提醒了我：把「done」变成可测试标准有独立价值，但不能据此声称 V2 还保留同一套 Sprint Contract 形式。保留验收职责与保留旧仪式不是一回事。

接口实现则可能重建。这是框架中的另一种选择，不是上述跨任务费用数字已经证明的结论。

## 两种姿态，同一种判断力

Build to Delete 和 Build to Last 不是对立的设计哲学。它们是同一个系统在不同职责上的设计姿态——不只面对模型的大脑和现实世界的手脚，也面对必须有人负责的边界。

知道哪些存在前提需要复核、哪些职责仍然承重，以及「会留下来」的实现什么时候值得重建——这是 Agent 时代重要的判断力。

好消息是判断的前提可以学：先查职责。在加任何组件之前，问自己它为什么存在；在删任何组件之前，问自己什么证据说明可以删，以及删掉后谁继续承担责任。

这回到了 [无序 Vibe Coding 的隐性代价](https://nexus.sigmoid.cc/无序%20Vibe%20Coding%20的隐性代价/) 中讨论过的线索：机械性的编码正在被自动化，工程师的判断责任却没有消失。Build to Delete 和 Build to Last 的区分是这种判断力的一个具体操作——不是永久分类表，而是每天坐下设计系统时可以用上的审计框架。
