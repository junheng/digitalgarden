## 当期技术日报：MCP工具调用的幂等与恢复

**RPC成功、任务完成与外部结果如何区分**

核对日：2026-11-03（Asia/Shanghai）。资料核对窗口为北京时间02:27—02:30。本期为官方规范机制分析，**不是宣称当日新发布的新闻**。示例均明确合成，未使用私人来源、真实项目案例或运行事故。

结论是：不要把一份正常RPC响应当成一张通用的业务成功证明。通信、工具结果、任务生命周期和业务验收有不同判据。恢复应围绕原操作的可查询身份展开；协议请求ID不是幂等键，取消也不是外部效果自动撤销。

## 一、版本先行：这次核对改变了什么

MCP官方Versioning页面当前列出 **2026-07-28**。这是协议修订标识，不等于所有关联网页的实际发布日期；网页未显示独立发布时间的，不以版本日期伪造精确发布日期。官方当前更新说明Major changes第6、9项确认：任务移至官方扩展 `io.modelcontextprotocol/tasks`；移除响应流的事件重放机制。[版本依据](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning#revisions)、[变更依据](https://modelcontextprotocol.io/specification/2026-07-28/changelog#major-changes)。

| 核对面 | 2025-11-25文档 | 2026-07-28当前文档 |
|---|---|---|
| 异步结果 | 核心中的实验性Tasks；`tasks/result`取最终结果 | 独立Tasks扩展；`tasks/get`内联终态结果/错误；`tasks/update`提供输入 |
| 创建方式 | 请求携带task参数；有逐工具taskSupport约定 | 客户端每请求声明扩展能力；服务器决定是否返回task句柄 |
| 断开的HTTP响应流 | 不应视为取消；可选事件重放 | 关闭SSE响应流即该请求取消；无Last-Event-ID恢复 |

**适用边界**：这里比较文档契约，不声称任意现有服务均已实现新版本。真实客户端必须根据双方实际协议及扩展能力分支，不能把不同版本字段混用。旧版只用于明确对照。[旧任务](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)、[旧传输](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#resumability-and-redelivery)。

## 二、四层判断，不是四种互斥状态

| 层次 | 足够说什么 | 仍需核对什么 |
|---|---|---|
| RPC响应 | 本次请求得到匹配的result或error | result可能是阶段性响应；error也不证明外部绝无副作用 |
| 工具业务结果 | 检查 `isError` 和具体业务字段 | `isError:false` 或缺省不能代替产物内容验收 |
| 异步任务 | 句柄表示受理；终态表示该任务生命周期结束 | completed可带业务错误；failed含JSON-RPC错误；取消与业务回滚分开 |
| 外部效果 | 按事先定义的目标核验对象、版本和回执 | 回执可能仅证明受理；对象存在也未必内容正确 |

官方Tools的Error Handling区分协议错误与工具执行错误。后者可在JSON-RPC `result`内以 `isError:true`返回，因此“有result”不推出“业务成功”。官方任务扩展更明确：工具业务报错可以进入 `completed`，`failed`用于JSON-RPC执行错误。[工具错误](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#error-handling)、[任务状态](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html#task-status)。

**分析**：四层判断没有构成一套MCP强制的验收状态机。尤其“外部效果已验证”是本文建议的业务判据。工具的错误结果可能发生在部分写入之后；规范并未赋予错误标志全局回滚含义。

**合成例子**：公开数据导出工具返回句柄，只可称“已受理”；任务completed但result.isError为true，只可称“执行结束、导出失败”；result报告成功，还要按目标核验对应数据版本和文件。若文件写入后下载链接生成失败，业务失败与部分效果可能并存。这是机制推演，不是已观察事故。

## 三、幂等键、请求ID和任务ID各管什么

RPC请求ID用于关联响应。当前基础规范要求未收到响应的请求不能重复使用ID；当前传输变化要求中断后作为新请求重发并使用新ID。二者都没有规定“同ID自动去重”。[基础消息](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#requests)、[当前变化第9项](https://modelcontextprotocol.io/specification/2026-07-28/changelog#major-changes)。

| 身份 | 工程用途 | 重试/恢复时的建议 |
|---|---|---|
| request ID | 某次通信尝试 | 按协议生成新请求ID，不把它当去重数据库 |
| taskId | 服务器创建的持久任务 | 查询原taskId；注意TTL、授权和服务端作用范围 |
| 业务操作ID/幂等键 | 同一次业务意图 | 接口明确支持时，同意图同参数重试保留原键 |
| 外部对象ID/版本/回执 | 核对实际效果 | 关联业务意图，明确证明的是受理、生成还是最终生效 |

HTTP RFC 9110 §9.2.2把幂等限定为重复请求具有相同的**预期效果**，不是相同响应，也不是内部代码只执行一次。MCP调用通过POST承载，不能借HTTP的幂等方法分类替所有工具宣布安全重试。[RFC §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

Stripe官方说明提供的是**特定服务、特定API版本**的契约：API v1在端点开始执行后保存首次同键请求的状态与正文，包括500响应；参数不一致报错；键至少24小时后可被清理，清理后复用可能创建新请求。验证失败或并发冲突等尚未开始执行的情况不保存相同类型的幂等结果。其v2另有恢复语义，不能套用v1规则。[官方幂等说明](https://docs.stripe.com/api/idempotent_requests)。

**工程建议**：去重必须落实到会产生副作用的边界；键至少关联调用者、操作类型和规范化参数摘要，明确保留期限、并发处理和下游透传规则。不要在参数变化后沿用旧键，也不要为绕过错误自动生成新键。客户端随机放一个字段不构成服务端承诺。

## 四、unknown是证据判断，恢复是查询原操作

**分析**：响应未到时，客户端无法仅凭超时区分“未收到”“正在执行”“效果已产生而响应丢失”。本文以unknown表示这种本地知识状态，**不是Tasks规范新增状态**。

建议的恢复顺序：

1. 提交前持久保存业务意图、参数摘要和已支持的幂等身份。
2. 收到taskId后保存关联；断线后查询原taskId，按 `pollIntervalMs` 控制频率。
3. `input_required`走 `tasks/update`；completed检查内联工具结果；failed读取错误；cancelled按契约解释。
4. 根据业务目标查询外部对象和原回执。任务找不到可能是TTL后清理，不能推出业务从未执行。
5. 任务句柄未收到时，使用业务层明确提供的幂等重放/原回执查询；该能力若不存在，就保留unknown，停止自动制造新副作用。

当前扩展无 `tasks/list`，也未为所有工具统一定义幂等键或“按业务键找回任务”的接口。不能凭空查询一个未收到的taskId。记录过期、查证入口缺失，都应当是工具设计时明确暴露的限制。[任务轮询](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html#task-polling)、[任务错误](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html#error-handling)。

## 五、重发、重试与取消的边界

| 情形 | 建议动作 | 不足以得出的结论 |
|---|---|---|
| 输入错误 | 修正输入后重新请求 | 同参数多试几次就会好 |
| 暂时网络/限流 | 按契约有限退避；先判断副作用和去重能力 | 每个POST都可以自动重做 |
| 同键已保存500 | 读取服务契约、查询原操作 | 新键能“修复”原操作且没有重复风险 |
| 任务仍working | 查询原任务 | 新提交同参数就是恢复 |
| unknown写操作 | 原任务/原回执查证 | 没回响应就是没执行 |
| 取消ack | 表示取消意图被接收 | 已取消终态、已回滚、外部对象已删除 |

HTTP 202的标准语义是受理但未完成，HTTP规范并没有让状态码替异步业务报告最终结局。MCP中具体何时使用202还需遵守相应传输规则，不能把通用202例子当成任务创建响应格式。[RFC §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)。

当前HTTP关闭响应流触发对该请求的取消；这不等于已提交到外部系统的写入自动撤销。Tasks扩展中的 `tasks/cancel` 则明确是协作式：ack后状态可能仍working，也可能最终到达其他终态，规范甚至允许客户端取消后不再轮询。**建议**：若产品要向用户证明取消最终效果，就额外保留业务查证；这是高于最小协议动作的产品策略。[请求取消](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation#transport-specific-cancellation)、[任务取消](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html#task-cancellation)。

## 六、反方复核与未证实部分

1. **是否一定要四重查询？** 不必。若同步工具已有可信且足够的最终回执，可直接按它验收。四层框架是区分语义，不是强制增加网络请求。
2. **是否只能停在unknown？** 不必。支持幂等及结果查询的服务可恢复；但应以具体保留窗口和下游契约为条件。
3. **任务持久是否等于永远可查？** 否。TTL及清理是明确边界，不能用持久句柄推导无限保存。
4. **exactly once能否在某些范围成立？** 可以讨论特定事务域、保留窗口及故障模型；本文未测试实现，不对任意MCP工具做全局保证。先记录成功后做业务可能漏做；反过来可能重复。跨系统效果与记录之间的原子性需单独设计。
5. **回执是否绝对可信？** 不。它依赖服务端实现与来源可信度，摘要只能比较字节，不能自动证明语义正确。

本期只有官方文档核对与机制推演，没有进行真实MCP服务故障注入、并发去重、支付、导出或取消实验。本文仅分析公开契约，不涉及私人案例。

## 七、实践落点与术语

建议先改两处：把通信结果、任务状态、业务结果和外部回执分开记录；为每个有副作用的工具写明“超时查原操作、同键重试条件、取消不等于撤销”的契约。这些是工程建议，不是MCP新增的统一保证。

| 英文 | 中文 | 本文首次语境 |
|---|---|---|
| RPC | 远程过程调用 | 一次请求与响应 |
| idempotency key | 幂等键 | 业务意图去重 |
| receipt | 回执 | 外部效果证据 |
| unknown | 结果未知 | 客户端证据状态 |
| exactly once | 恰好一次 | 需明确范围的效果保证 |

来源证据等级：官方规范用于解释契约，厂商文档仅证明该厂商所声明接口语义；二者都不是实现正确性的实测证明。下方列出版本与原文定位，以便回查。
